# Schema publishing

Schema publishing is how WordLift turns the entities in your Knowledge Graph into schema.org JSON-LD for each URL and delivers it to your pages. You choose where that JSON-LD is injected: in the browser, on your server, in a cache filled ahead of time or at the edge.

## How WordLift selects structured data for a URL

An entity's `schema:url` property links it to a page. When WordLift publishes structured data for a URL, it selects the entities linked to that URL and the entities connected to them.

The [Data API](/apis-and-sdks/data-api/) does the selection and returns the result as JSON-LD. Its endpoint is `https://api.wordlift.io/data/{page-url}`, where the page URL is written as a path with `https://` rewritten as `https/`:

```text
https://api.wordlift.io/data/https/example.org/page.html
```

On a multilingual site, the `__wl_lang` query parameter takes an ISO 639-1 language code and selects the graph for that language. The WordLift Cloud script derives it from the `lang` attribute of the `html` element. See [Multilingual](/platform/knowledge-graph/multilingual/).

After a GraphSync run updates your graph, the Data API returns the updated JSON-LD for the affected URLs.

## Delivery options

| Option | Where the JSON-LD is injected | In the initial HTML | Best fit | Guide |
| --- | --- | --- | --- | --- |
| WordLift Cloud script (`bootstrap.js`) | In the browser DOM, after the script runs | No | You can add a script to the page but don't control server-side rendering, and setup speed matters most. | [Install WordLift Cloud](/welcome/install-wordlift-cloud/) |
| WordPress plugin (existing installs) | Generated by the plugin from your annotations, shaped by Mappings | See the guide | Existing installs of the classic WordLift plugin. | [JSON-LD](/integrations/wordpress-plugin/jsonld/) |
| Server-side rendering with the Data API | In your server, static-site generator, edge function or framework, before the HTML is returned | Yes | You control the rendering pipeline and need the markup in the raw HTML. | [Data API](/apis-and-sdks/data-api/) |
| Out-of-band cache prefill | In server-rendered HTML, read from a shared cache that a scheduled job fills | Yes | Canonical URLs are known and daily freshness is acceptable. | [Out-of-band cache prefill](/apis-and-sdks/data-api/out-of-band-cache-prefill/) |
| Cloudflare edge | In the `head` element, inserted by a Cloudflare Worker with `HTMLRewriter` | Yes | Your site is already behind Cloudflare. | [Cloudflare integration](/apis-and-sdks/data-api/cloudflare-integration/) |

### WordLift Cloud script

Place `bootstrap.js` from `https://cloud.wordlift.io/app/bootstrap.js` in the `head` of each page with the `async` attribute. The script detects the page URL, fetches the JSON-LD from the Data API and adds it to the page. Google Tag Manager is the only supported alternative loader. The script uses no cookies, so it doesn't need to sit behind cookie consent.

### WordPress plugin

The classic WordPress plugin generates JSON-LD from the entities you annotate in your content. Mappings, built on Advanced Custom Fields, let you shape the output for any schema.org type. The plugin is documented for existing installs; new customers start with WordLift Cloud.

### Server-side rendering with the Data API

Your application determines the canonical URL, builds the Data API URL, fetches the response, serializes it as JSON and injects it in a `script` element with `type="application/ld+json"`. Parse and serialize the response with your runtime's JSON tools instead of building JSON-LD by string concatenation.

The Data API targets a response time under 200 ms. This is a target, not a guarantee, so never make page rendering depend on an uncached Data API call with no timeout or fallback. For request-time caching, use a stale-while-revalidate pattern.

### Out-of-band cache prefill

A scheduled job fetches and validates the JSON-LD for a known set of public content pages and stores it in a shared persistent cache. The page renderer reads only from that cache, so Data API requests stay out of the rendering path. The starting configuration refreshes every 24 hours with a 30-hour cache TTL.

### Cloudflare edge

A Cloudflare Worker Route fetches the origin page and the page's JSON-LD, then inserts the JSON-LD into the `head` element with `HTMLRewriter`. It doesn't load `bootstrap.js`. If the Data API fails, the Worker returns the origin response unchanged.

## Choose client-side or server-side

With the WordLift Cloud script, JSON-LD is added to the rendered DOM after the browser runs `bootstrap.js`. It is not in the initial HTML response. This works for crawlers that render JavaScript, including Googlebot.

AI crawlers, retrieval systems and agentic tools don't all process pages the same way. Some render JavaScript, some rely on search engine indexes and some read only the raw HTML. When AI search visibility, answer engine optimization (AEO), generative engine optimization (GEO) or non-JavaScript crawlers are a primary requirement, prefer server-side delivery, so the JSON-LD is in the HTML your server returns.

Client-side delivery remains useful when setup speed and minimal application changes matter most, or when the main consumer is known to render JavaScript.

## Move from client-side to server-side

If you already publish with the WordLift Cloud script, you can move JSON-LD injection into your rendering layer. The server-side Data API returns a JSON-LD document, while legacy client-side responses can be a top-level array, so follow [Migrate to the server-side Data API](/apis-and-sdks/data-api/migrate/) instead of copying old property paths.

## Check the published markup

- **Validate the markup:** Use Google's [Rich Results Test](https://search.google.com/test/rich-results) or your preferred structured data validator.
- **Client-side delivery:** Inspect the rendered DOM. JSON-LD added by `bootstrap.js` does not appear in the raw page source.
- **Server-side, prefill or edge delivery:** Check the raw HTML response. The `application/ld+json` script must be there before any JavaScript runs.
